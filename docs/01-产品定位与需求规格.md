## 1.1 术语与标识约定

本节定义全文档集统一使用的名词与标识，其他文档不得另起别名。

| 术语 | 含义 | 备注 |
| --- | --- | --- |
| 青垣面板 | 产品名，英文 Qingyuan Panel | 代号 qingyuan |
| 控制面（Panel） | 提供 Web 界面与 API 的中心服务，二进制 `novapanel` | 默认端口 34567（HTTPS） |
| 被控端（Agent） | 部署在受管服务器上的常驻进程，二进制 `nova-agent` | gRPC 端口 34568 |
| 命令行（CLI） | 本机运维工具，二进制 `novactl` | 与控制面同机部署 |
| 节点（Node） | 一台被纳管的服务器，等价于一个 Agent 实例 | 主节点即控制面所在机器 |
| 租户（Tenant） | 资源隔离单元，所有业务表带 `tenant_id` | v1.0 仅单租户默认值 1 |
| 作业（Job） | 一次可追踪的异步执行单元，含目标节点、幂等键、结果 | 表前缀 `job_` |
| 应用（App） | 应用商店中可一键部署的软件模板 | 表前缀 `app_` |
| 指标点（Point） | 一条时序采样记录，含 metric、labels、ts、value | 表前缀 `mon_` |

目录与端口基线：

| 项 | 路径 / 值 |
| --- | --- |
| 安装根目录 | `/opt/novapanel` |
| 数据目录 | `/opt/novapanel/data` |
| 主配置文件 | `/opt/novapanel/conf/panel.yaml` |
| 日志目录 | `/opt/novapanel/logs` |
| 面板 HTTPS 端口 | 34567 |
| Agent gRPC 端口 | 34568 |

标识规范：

- 权限标识 `module:resource:action`，`action` 取值 `list` / `read` / `create` / `update` / `delete` / `exec` / `export`。
- 错误码 6 位 `MMSSNN`，`MM` 为模块号，`SS` 为资源号，`NN` 为序号，详见 [3.8 errs 包与错误码规范](./03-技术栈与工程规范.md#38-errs-包与错误码规范)。
- API 前缀 `/api/v1`，资源名复数、多词用中划线，例如 `/api/v1/cluster-nodes`。

## 1.2 产品定位与目标场景

### 1.2.1 一句话定位

青垣面板 是一款开源、单二进制交付的**多节点服务器运维管理面板**，把网站托管面板的易用性与集群管理平台的可控性合到一处：一个控制面纳管数百台 Linux 服务器的网站、数据库、容器、监控与安全基线，且所有操作可审计。

### 1.2.2 定位坐标

传统面板（宝塔、aaPanel、cPanel）解决「一台机器上把网站跑起来」；云原生平台（Rancher、KubeSphere）解决「一个 K8s 集群怎么管」。中间存在明确空缺：**几台到几百台裸机或云主机、以 Docker 与传统 LNMP 混合承载业务、没有 K8s 也不打算上 K8s 的团队**。青垣面板 面向这一段。

```text
易用性高
    ^
    |   宝塔/aaPanel        青垣面板
    |   (单机、闭源商业)     (多节点、开源、可审计)
    |
    |   Cockpit             Rancher/KubeSphere
    |   (单机、系统层)       (K8s、重、学习曲线陡)
    +---------------------------------------> 规模与可控性
```

### 1.2.3 目标场景

| 编号 | 场景 | 典型规模 | 核心诉求 | 对应模块 |
| --- | --- | --- | --- | --- |
| S1 | 个人/小团队多台 VPS 集中管理 | 2-10 节点 | 一处登录管全部机器，别再逐台 SSH | 集群节点、Web 终端、网站 |
| S2 | 中小企业混合部署运维 | 10-80 节点 | 传统 PHP/Java 站点与 Docker 服务并存 | 运行环境、容器与编排 |
| S3 | MSP 代运维多客户资产 | 50-500 节点 | 客户隔离、操作留痕、批量巡检与交付报告 | 租户、审计、批量作业 |
| S4 | 企业内部平台组自建 PaaS 底座 | 100-500 节点 | 二次开发、对接内部 SSO 与告警通道 | OpenAPI、插件、Webhook |
| S5 | 信创与等保合规环境 | 20-200 节点 | 国产 OS 与 arm64 支持、安全基线与审计导出 | 安全审计、兼容性 |

### 1.2.4 产品价值主张

| 对象 | 现状痛点 | 青垣面板 给出的改变 |
| --- | --- | --- |
| 站长 | 装面板要挑发行版，升级容易崩 | 单二进制 + 免 CGO，一条命令装完，升级即换二进制 |
| 运维工程师 | 批量操作靠自写脚本，失败无回溯 | 批量作业带幂等键与逐节点结果，失败可重放 |
| 技术负责人 | 谁改了生产配置说不清 | 全量审计流水 + 变更前后差异快照 |
| 安全合规 | 面板本身就是入口风险 | mTLS、二次校验、命令黑名单、会话录制 |

## 1.3 目标用户角色画像与痛点

### 1.3.1 个人站长 / 独立开发者

| 维度 | 描述 |
| --- | --- |
| 技术水平 | 会基本 Linux 命令，不写 Ansible，不碰 K8s |
| 资产规模 | 2-10 台 VPS，20-50 个站点，多为 WordPress、Typecho、静态站 |
| 使用频次 | 每周 1-3 次，多为发版、续证书、查为什么打不开 |
| 核心痛点 | 面板装在每台机器上，各自一个地址一个密码；证书续期失败无提醒；磁盘满了才发现 |
| 关键诉求 | 一个入口看全部；证书与磁盘自动告警；一键备份到对象存储 |
| 成功指标 | 15 分钟内完成「加节点 → 建站 → 上 HTTPS → 配备份」 |

### 1.3.2 中小企业运维工程师

| 维度 | 描述 |
| --- | --- |
| 技术水平 | 熟练 Shell 与 Docker，能读日志定位问题，写过简单脚本 |
| 资产规模 | 10-80 台服务器，混合 PHP/Java/Node 与 Docker 服务，含测试与生产环境 |
| 使用频次 | 每天多次，日常巡检、发布、扩容、处理告警 |
| 核心痛点 | 批量操作靠 for 循环 SSH，中途失败不知道哪几台没成功；容器和传统服务两套工具；开发要日志得找运维 |
| 关键诉求 | 批量执行带逐节点结果；容器与传统服务同一界面；把只读权限开放给开发 |
| 成功指标 | 批量升级 50 台的一个软件包，5 分钟内拿到成功/失败清单并可对失败项重试 |

### 1.3.3 MSP 托管服务商

| 维度 | 描述 |
| --- | --- |
| 技术水平 | 团队分层，含初级值班与高级工程师 |
| 资产规模 | 50-500 台，横跨多个客户与多家云厂商 |
| 使用频次 | 全天候值班使用 |
| 核心痛点 | 客户资产必须隔离；出问题要能证明「不是我们改的」；月度巡检报告靠人工截图 |
| 关键诉求 | 租户隔离与分级授权；完整审计流水可导出；批量巡检自动出报告 |
| 成功指标 | 任一操作可在 30 秒内回答「谁、何时、在哪台、改了什么、改前是什么」 |

### 1.3.4 企业内部平台组

| 维度 | 描述 |
| --- | --- |
| 技术水平 | 自研能力强，Go/Java 后端与前端齐备 |
| 资产规模 | 100-500 台，作为内部 PaaS 的底座 |
| 使用频次 | 以 API 调用为主，界面为辅 |
| 核心痛点 | 商业面板不给源码不给 API，无法嵌入内部流程；对接内部 SSO 与告警平台无扩展点 |
| 关键诉求 | 完整 OpenAPI 与机器人账号；插件与 Hook；能作为组件嵌入自有门户 |
| 成功指标 | 不改 青垣面板 源码即可完成 SSO 对接与告警转发 |

## 1.4 竞品横向对比

### 1.4.1 总体对比表

| 维度 | 宝塔面板 BT | 1Panel | aaPanel | cPanel | Cockpit | 青垣面板 |
| --- | --- | --- | --- | --- | --- | --- |
| 架构 | Python + Nginx，单机脚本式 | Go + Vue，单机为主 | 同 BT 国际版 | Perl/C++ 单机 | C + systemd/D-Bus | Go + Vue，Server-Agent |
| 部署形态 | 在线安装脚本，依赖系统 Python | 单二进制 + Docker | 在线安装脚本 | 商业安装器 | 发行版软件包 | 单二进制，前端 embed |
| 多节点 | 需企业版，节点为独立面板 | 有节点管理，能力有限 | 同 BT | 无（WHM 为多账号非多机） | 有 Dashboard 多机，仅系统层 | 原生集群，统一作业与批量执行 |
| 容器 | 有 Docker 模块，偏基础 | 强，以容器为核心 | 同 BT | 弱 | Podman 基础管理 | Docker API v1.45 + Compose 编排 + 私有仓库 |
| 监控告警 | 基础曲线 + 简单告警 | 基础监控，告警较弱 | 同 BT | 资源统计 | 实时图无历史留存 | 内置时序库、规则引擎、多通道通知、静默抑制 |
| 权限模型 | 单管理员为主，子账号弱 | 有用户与角色，粒度粗 | 同 BT | 账号分级完善 | 依赖系统用户与 sudo | Casbin RBAC + 租户域 + 资源级 + 七种 action |
| 审计 | 操作日志简单 | 有日志，不成体系 | 同 BT | 有访问日志 | 依赖 journald | 全量审计流水 + 变更差异 + 终端录制 + 导出 |
| 开源协议 | 闭源（部分脚本可见） | Apache-2.0 | 闭源 | 商业闭源 | LGPL-2.1 | Apache-2.0 |
| 商业化 | 付费插件 + 企业版 | 开源 + 商业版 | 付费插件 | 按许可收费 | 无（随发行版） | 开源核心，企业能力以插件提供 |
| 主要短板 | 闭源、上报争议、多机弱 | 集群与告警弱，传统 LNMP 支持不如 BT | 同 BT | 贵、仅 RHEL 系、无容器 | 无网站/数据库/应用管理 | 生态与插件积累少（v1.0 起点） |

### 1.4.2 关键差距量化

| 能力 | 竞品普遍水平 | 青垣面板 v1.0 目标 |
| --- | --- | --- |
| 单控制面可管节点数 | 1（或数十，能力受限） | 500 |
| 批量执行结果粒度 | 汇总成功/失败 | 逐节点 stdout/stderr/退出码/耗时 |
| 指标保留时长 | 7-30 天原始点 | 原始 7 天 + 5 分钟粒度 30 天 + 1 小时粒度 1 年 |

| 审计可追溯 | 操作名 + 时间 | 操作名 + 节点 + 参数 + 变更前后 + 结果 + traceId |
| 权限最小单位 | 菜单 | 资源实例 + action |

## 1.5 差异化取舍

### 1.5.1 四大差异化重点

| 重点 | 具体做法 | 与竞品的区别 |
| --- | --- | --- |
| 多节点集群纳管 | Agent 反向拨号建立 mTLS 双向流；节点分组与标签；批量作业带幂等与逐节点结果；节点离线操作排队 | 竞品多为「多个独立面板的聚合视图」，青垣面板 是单一控制面统一编排 |
| 容器与编排 | 直连 Docker Engine API v1.45；Compose 项目全生命周期；镜像仓库凭据管理；容器指标与日志统一入口 | 传统面板把 Docker 当附属模块，青垣面板 视为一等公民与传统服务并列 |
| 监控告警与可观测 | 内置时序表三级降采样；规则引擎支持持续时长与组合条件；告警分级、静默、抑制；通知多通道模板化 | 竞品仅有实时曲线与单阈值告警，缺历史留存与抑制机制 |
| 安全合规与审计 | mTLS 双向认证、2FA、命令黑名单、危险操作二次确认、终端会话录制回放、审计流水导出 | 竞品审计多为操作名列表，无法还原变更内容 |

### 1.5.2 明确的取舍

取舍即「为了做好上面四件事，我们主动放弃什么」。

| 取舍项 | 决定 | 理由 |
| --- | --- | --- |
| 不做 Kubernetes 管理 | 放弃 | 与 Rancher/KubeSphere 正面竞争无胜算，且目标用户明确不上 K8s |
| 不做 Windows 被控端 | v1.0-v2.0 均放弃 | 系统调用抽象成本高，目标场景中占比 < 3% |
| 不做邮件服务器管理 | 放弃 | cPanel 强项，维护成本极高，收益低 |
| 不做可视化 DNS 服务托管 | 仅做 DNS 服务商 API 对接（用于 ACME） | 自建权威 DNS 超出运维面板边界 |
| 不追求 LNMP 编译选项的极致灵活 | 提供固定优化的预编译包 + 少量开关 | 竞品在此堆了十年，正面比拼不划算 |
| 不做插件市场收费分成 | 开源核心 + 官方企业插件 | 生态初期先保证质量与安全 |
| 不做移动端完整功能 | 仅移动端响应式查看与告警确认 | 运维变更操作在小屏上风险高 |
| 不做多副本双活（v1.0） | v1.0 提供可选的**双副本主备**（外置库 + Redis 选主，见 14.12），默认形态仍为单实例 + 定时备份；无状态多写与跨机房双活 v2.0 评估 | 双活需解决 cron、告警评估、Agent 长连接三类难以无锁并发的状态，成本与目标规模不匹配；先把 500 节点做稳 |

### 1.5.3 迁移友好性

为降低从存量面板迁入的门槛，v1.0 提供只读导入能力：

| 来源 | 导入内容 | 形式 |
| --- | --- | --- |
| 宝塔面板 | 站点清单、域名、根目录、PHP 版本、伪静态、数据库清单 | 读取本机配置生成导入预览，人工确认后落库 |
| 1Panel | 站点与容器清单 | 同上 |
| 裸 Nginx | server 块解析为站点 | 解析 `nginx.conf` 及 include 目录 |

导入只创建 青垣面板 侧元数据与接管关系，不改写原有配置文件；接管确认后才生成 青垣面板 托管配置。

### 1.7.3 权限约束规则

1. 越权授予禁止：任何角色只能授予自己已持有的权限子集。
2. 审计员写权限硬禁止：`auditor` 角色在代码层面拒绝所有非 `list/read/export` 的 action，即便策略被误配。
3. 机器人限制：`api_bot` 无 `term:session`、`user:*` 与 `ops:setting` 权限；密钥必须设置有效期，最长 365 天。
4. 危险操作强制二次校验：节点下线、数据库删除、恢复覆盖、面板升级需重新输入密码或 TOTP。
5. 数据隔离：除 `super_admin`，所有查询强制注入 `tenant_id` 条件，由 repository 层统一拼接，不依赖调用方自觉。

## 1.8 核心用户故事与验收标准

每条故事编号为 `US-模块缩写-序号`，验收标准使用 Given-When-Then，全部 P0 故事必须有对应自动化测试用例编号（见 [测试与质量保障](./14-测试与质量保障.md)）。

### US-NODE-01 纳管新节点

作为运维工程师，我希望复制一条命令在新服务器上执行即可完成纳管，以便快速扩容。

| 编号 | 验收标准 |
| --- | --- |
| AC-1 | Given 已登录且有 `cluster:node:create` 权限，When 打开「添加节点」，Then 生成含一次性 token（有效期 30 分钟、仅可用一次）的安装命令 |
| AC-2 | Given 目标机器可出网访问控制面 34568，When 执行安装命令，Then 90 秒内节点出现在列表且状态为 online，系统信息与 Agent 版本完整 |
| AC-3 | Given token 已被使用或过期，When 再次执行同一命令，Then 安装脚本报错退出（错误码 200011），不产生半注册节点 |
| AC-4 | Given 目标机器在 NAT 后且无公网 IP，When 执行安装命令，Then 仍能成功纳管（Agent 仅出站） |
| AC-5 | Given 网络中断 5 分钟后恢复，When 观察节点状态，Then 自动从 offline 恢复 online，期间指标从本地缓冲补传且无重复点 |

### US-NODE-02 批量执行命令

作为运维工程师，我希望对一组节点执行同一命令并看到每台的结果，以便定位失败机器。

| 编号 | 验收标准 |
| --- | --- |

### 1.12.3 明确的非目标

- 不追求成为「什么都能干」的一体化平台，宁可少做而做深四大差异化重点。
- 不以牺牲可审计性换取操作便捷（例如不提供无记录的免密快捷执行）。
- 不为兼容 EOL 系统（如 CentOS 7）而降低技术选型标准。
- 不做「静默上报」类遥测；任何数据外发均需用户显式开启并可查看发送内容。

### 1.13.2 需求追溯

每条功能需求在开发阶段必须建立追溯链，缺失任一环节不允许合入：

```text
功能条目（1.6 表格行）
  → 用户故事编号（US-XXX-NN）
    → API 接口（05 号文档中的路径与错误码）
      → 数据表（04 号文档中的表与字段）
        → 前端页面（06 号文档中的路由与组件）
          → 测试用例编号（15 号文档）
```

| --- | --- | --- |
| 需求编号 | 本文档 1.6 与 1.8 | 产品负责人 |

### 1.13.3 变更管理

| 变更类型 | 处理方式 |
| --- | --- |
| P0 功能删减 | 必须重新评审，且更新本文档版本号与变更记录 |
| 优先级调整 | 由产品负责人决定，记录在本节变更表 |
| 新增需求 | 默认进入下一个小版本，不插入当前迭代 |
| 基线约定变更（端口、目录、错误码分段、命名规范） | 需架构评审通过，并同步更新 02、03、04、05 号文档 |
